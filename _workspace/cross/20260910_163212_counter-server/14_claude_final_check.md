## 3. 확정 해석 (구현자 필수 준수)

통합 과정에서 정밀도가 빠진 2건을 아래로 확정한다. 어느 쪽도 조정 결정을 뒤집지 않으며, 이미 채택된 결정(P-C4 방향·D3 16B)을 실행 가능한 형태로 못 박는 것이다. **베이스 문서의 상충 문장보다 아래가 우선한다.**

### [F-1] Med — 수정 10의 "`EchoExample.Tests` 참조 관례"는 그대로 따를 수 없다 → **public 확정**

`EchoExample.Tests.csproj`를 실측한 결과 그 관례는 **`ServerLib` 한 개만 `ProjectReference`하고, exe 프로젝트 참조도 `InternalsVisibleTo`도 전혀 없는** 구성이다(`EchoExample.Tests.csproj:17-20`, 18행 주석 *"public API만 사용 (internal 접근 불필요, InternalsVisibleTo 대상이 아님)"*). 즉 "접근 허용은 기존 csproj 방식을 따른다"는 문장이 가리키는 **기존 방식 자체가 존재하지 않는다.** 반면 통합 계획은 테스트가 실제 `CounterState`·`CounterHandler`·`CounterScenario`를 호출할 것을 요구한다(베이스 §2 테스트 csproj 행 "서버·클라이언트·ServerLib 참조", 베이스 §6 "알고리즘을 복제하지 않고 실제 내부 핸들러와 실행기를 호출", 그리고 D4가 seam 테스트를 삭제하며 내세운 대체 근거 "E2E가 실제 `CounterScenario` 실행"). 지시와 관례가 맞물리지 않는다.

**확정:**
1. `CounterState`·`CounterHandler`·`CounterScenario`는 **`public`** 으로 선언한다.
2. **`InternalsVisibleTo`를 사용하지 않는다.**
3. `CounterExample.Tests`는 `CounterServer`·`CounterClient`·`ServerLib` 3개를 **평범한 `ProjectReference`** 로 참조한다.
4. 이 확정으로 **무효화되는 베이스 문장 3곳**: 베이스 §3 *"카운터 상태·핸들러·시나리오는 예제 프로젝트의 `internal` 구현으로 둔다"*, 베이스 §2의 `CounterServer.csproj`·`CounterClient.csproj` 행 *"테스트 어셈블리에만 내부 접근 허용"* (2행).

**이 방향을 택하는 결정적 근거(동전 던지기가 아님):** `InternalsVisibleTo`를 **두 개의** exe 프로젝트에서 걸면 각 exe의 암묵 `internal partial class Program` 두 개가 동시에 테스트 어셈블리에 노출되어, 테스트가 `Program`을 비수식 참조하는 순간 CS0104(모호한 참조)가 된다. public 방향에는 이 위험이 없다. 예제 exe의 타입은 NuGet 배포 대상(`pack.ps1`)이 아니므로 public화해도 공개 표면이 넓어지지 않으며, **ServerLib 쪽 캡슐화(Transport `internal`)는 그대로 유지**되므로 프로젝트 규칙 위반이 아니다.

### [F-2] Med — 베이스에 남은 `CounterValuePacket` "8바이트" 기술 → **전부 16으로 읽는다**

D3으로 16B가 확정됐으나 베이스 문서에는 8B 기술이 **명시 3곳 + 암시 1곳** 남아 있다: 베이스 §1 L34 *"응답은 `long Value` 8바이트로 한다"*, **베이스 §5 L81 *"값 응답은 정확히 8바이트만 허용"***, 베이스 §6 L96 *"응답 ID=19와 본문 8"*, 베이스 §2 L41 *"`long Value` 직렬화"*. 통합 계획 머리말의 우선순위 규칙으로 형식상 해소되지만, **L81은 그대로 코드가 되는 검증 상수**라 명시 확정이 필요하다.

**확정:** 위 4곳은 전부 **16바이트(`long Value` + `long AppliedOps`)** 로 읽는다. 클라이언트의 응답 길이 검증 상수는 **16**이다. `AppliedOps`는 **검증을 통과해 실제 적용된 증감 op(Id 3·4)만** 계수하며 조회·드롭·미지 패킷은 제외한다. `Value`/`AppliedOps` 각각은 원자적이나 **쌍의 읽기는 원자적이지 않으므로 배리어 이후 정지 상태 조회에서만 함께 단언한다**는 제약을 `<remarks>`에 명시한다(수정 1이 이미 요구).

## 4. 잔여 지적 (비차단)

**[F-3] Low | D4의 대체 커버리지 주장이 과대하며, P-C3 수치 확정은 부분 반영.**
D4는 seam 테스트 삭제의 근거로 *"E2E가 실제 `CounterScenario` 실행"* 을 들었다. **삭제 판단 자체는 옳다**(내 P-C1 선택지 2). 그러나 시나리오를 호출하는 것은 배리어 **경로를 실행**할 뿐 배리어가 **필요하다는 것을 증명하지 않는다** — 배리어 결함은 비결정적 오값으로만 드러나고, 그것을 단언하려는 순간 flaky 테스트가 된다는 것이 P-C1 후반부의 지적이었다. 최종 보고에 *"배리어의 필요성은 어떤 테스트로도 결정적으로 증명되지 않으며, E2E는 '배리어 경로가 기대값을 산출한다'까지만 보장한다"* 를 한계로 기록할 것.
P-C3 관련: 수정 8이 E2E 주 시나리오 수치(8연결·+1,000/−750·Value 2,000·AppliedOps 14,000)를 고정한 것은 충분하다. 다만 `CounterStateTests`(태스크 수·반복 수·기대값), "단일 연결 증감", "총 연산 0" 3건은 여전히 수치가 없고 타임아웃도 구현자 재량이다. 구현자가 정하되 **전부 명명 상수로 두고 기대값을 `checked`로 계산**하면 리뷰 단계 판정 기준은 확보된다. 비차단.
